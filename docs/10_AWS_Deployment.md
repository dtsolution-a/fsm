# AWS Deployment Guide
## FSM — Shah Engineers and Consultants

**What this sets up:** the web admin panel + API on AWS, with a managed PostgreSQL 16 database, HTTPS-ready, with automatic backups and automatic rollback of bad releases. One command deploys; one command rolls back.

> **Status of this guide — read first.** The application changes (health checks, fail-fast config, rate limiting, same-origin routing) and the Docker build *steps* were verified on a developer machine (see §10). The **Terraform and Docker image builds themselves have NOT been run** — Terraform, Docker and an AWS account were not available while this was written. Expect to fix small things on the very first `bootstrap`/`release`; §9 lists the likely ones.

---

## 1. Architecture

```
                         Internet
                            │  HTTPS (ACM certificate)
                  ┌─────────▼─────────┐
                  │ Application Load  │   /api/*  ──►  backend  (NestJS, port 3001)
                  │ Balancer (2 AZs)  │   everything else ──►  web  (Next.js, port 3000)
                  └─────────┬─────────┘
          public subnets    │          (one origin for the browser: no CORS, no mixed content)
   ┌────────────────────────┴──────────────────────┐
   │  ECS Fargate   web ×N        backend ×N        │   security group: only the load balancer may connect
   └────────────────────────┬──────────────────────┘
          private subnets   │ 5432 (TLS)
                  ┌─────────▼─────────┐
                  │ RDS PostgreSQL 16 │   encrypted, 7-day backups, no public access
                  └───────────────────┘
 Secrets Manager: DB URL, JWT secret, first admin password   ·   ECR: images   ·   CloudWatch: logs + alarms
```

Why these choices:
- **Fargate, not servers:** nothing to patch or SSH into; a failed release rolls back by itself (circuit breaker).
- **RDS PostgreSQL 16:** matches the proposal; automated backups and point-in-time restore.
- **One load balancer, path routing:** the UI calls `/api/v1/...` on its own origin, so the same image works on any domain.
- **No NAT gateway:** app tasks sit in public subnets but only accept traffic from the load balancer; this saves roughly USD 35/month. The database has no route to the internet. For a stricter network later, move tasks to private subnets + NAT/VPC endpoints.
- **Secrets are generated by Terraform and live only in Secrets Manager** — nobody types or sees them, and they are not in the code.

## 2. Cost (rough, single task each, no high availability)

| Item | ≈ USD / month |
|---|---|
| Fargate (backend 0.5 vCPU/1 GB + web 0.25 vCPU/0.5 GB, running 24×7) | 30–35 |
| RDS `db.t4g.micro`, 20 GB, single-AZ | 15–20 |
| Application Load Balancer | 18–25 |
| Secrets Manager, logs, ECR, data transfer | 5–10 |
| **Total** | **≈ 70–90** |

These are estimates from memory, not live prices — check the AWS Pricing Calculator for Mumbai (`ap-south-1`) before committing. High availability (`desired_count = 2`, `db_multi_az = true`) roughly doubles the Fargate and database lines. The client funds hosting (Project Proposal §7).

## 3. Before you start (one-time)

1. An AWS account and an IAM identity with permission to create VPC, ECS, RDS, ECR, IAM roles, ALB, Secrets Manager, CloudWatch. Use SSO or an IAM user with MFA; **do not use root keys.**
2. Install: **AWS CLI v2**, **Terraform ≥ 1.6**, **Docker**. Then `aws configure` (or `aws sso login`) and check `aws sts get-caller-identity`.
3. (Recommended) create an S3 bucket + DynamoDB table for Terraform state and enable the `backend "s3"` block in `infra/terraform/versions.tf`. Without it the state file stays on the laptop that ran Terraform — losing it means losing control of the infrastructure.
4. `cp infra/terraform/terraform.tfvars.example infra/terraform/terraform.tfvars` and edit if wanted. Defaults work.

## 4. First deployment

```bash
bash infra/deploy.sh bootstrap   # creates the image registries only (services need images first)
bash infra/deploy.sh release     # builds both images, pushes, creates everything else (~15 min, mostly the database)
bash infra/deploy.sh seed        # one-off task: lookup lists + first admin user
```

Then:
```bash
bash infra/deploy.sh info        # shows app_url
aws secretsmanager get-secret-value --secret-id <admin_password_secret_arn> --query SecretString --output text
```
Open `app_url`, sign in with user ID **`Admin`** and that password, then **create your own admin user and change/deactivate the seed one**.

On Windows run these in **Git Bash** or **WSL**.

## 5. HTTPS and your own domain

1. In **ACM** (same region), request a certificate for e.g. `fsm.yourcompany.com`; validate it by the DNS record ACM shows.
2. Put the ARN in `terraform.tfvars` as `certificate_arn = "..."` and run `bash infra/deploy.sh release`. Port 80 then redirects to HTTPS.
3. In your DNS, create a `CNAME` (or Route 53 alias) from `fsm.yourcompany.com` to `alb_dns_name`.

Until a certificate is set the site is plain HTTP — **do not use it with real logins over the internet.**

## 6. Loading the QuikAllot data into the cloud database

The database is private, so import from a laptop through a short-lived SSM tunnel (no open ports, no SSH keys):

1. Set `create_bastion = true` in `terraform.tfvars`, run `bash infra/deploy.sh release`.
2. Install the AWS **Session Manager plugin**. Open the tunnel (leave it running):
   ```bash
   aws ssm start-session --target <bastion_instance_id> \
     --document-name AWS-StartPortForwardingSessionToRemoteHost \
     --parameters host=<db_endpoint>,portNumber=5432,localPortNumber=15432
   ```
3. In another terminal, take the password from the `database_url_secret_arn` secret and run:
   ```bash
   cd backend
   DATABASE_URL="postgresql://fsm:<password>@localhost:15432/fsm?schema=public&sslmode=require" npm run import:quikallot
   ```
   The import is safe to re-run. The report is written to `backend/import-report.json`.
4. Set `create_bastion = false` and release again to remove the helper machine.

## 7. Day-to-day

| Task | Command |
|---|---|
| Deploy a new version | `bash infra/deploy.sh release` (prints the release tag — note it) |
| Roll back | `bash infra/deploy.sh rollback <previous-tag>` |
| Watch logs | `bash infra/deploy.sh logs backend` (or `web`) |
| Database changes | Add a Prisma migration in `backend/prisma/migrations`; it is applied automatically when the new backend starts |
| Scale up | `desired_count = 2` (and `db_multi_az = true`) then `release` |

A release that fails its health checks is **rolled back automatically** by ECS. Database migrations run on container start; keep them backward-compatible (add columns/tables first, remove old ones in a later release) so a rollback never meets a schema it cannot read.

## 8. Backups, security and what is NOT included

**Included:** RDS encryption at rest, TLS to the database, automated daily backups kept 7 days with point-in-time restore, deletion protection and a final snapshot on destroy, private database, least-privilege security groups, secrets in Secrets Manager, security headers (helmet) and login rate limiting (10 attempts/min/IP), image vulnerability scanning on push, CloudWatch alarms for 5xx errors, database CPU and free storage.

**Restore:** RDS console → the instance → *Actions → Restore to point in time* creates a **new** instance; point `database_url` at it (or swap names). Take a manual snapshot before risky changes.

**Not included (decide with the client):**
- **Alarm notifications** — alarms exist but no SNS email/SMS is attached yet.
- **WAF** (AWS WAF in front of the load balancer) and CloudFront CDN.
- **Multi-AZ / 2+ tasks** — off by default to save cost; one task means a short outage during a task restart.
- **Staging environment** — set `environment = "staging"` with a separate state to create a second copy.
- **CI/CD pipeline** — deploys are run by a person with `deploy.sh`. A GitHub Actions workflow using OIDC can call the same script.
- **Email/SMS/WhatsApp, file uploads (S3), mobile push** — later phases.
- **Application-level MFA, password-reset email** — not built yet.

## 9. First-run problems to expect (untested infrastructure)

| Symptom | Likely cause / fix |
|---|---|
| `terraform init/validate` error mentioning `engine_version` | Set `engine_version = "16.4"` (or a currently supported 16.x) in `data.tf`. |
| ECS service stuck "no running tasks" | Images not pushed yet — run `release`, not only `terraform apply`. Check the service *Events* tab. |
| Backend tasks restart in a loop | `bash infra/deploy.sh logs backend`. Usually the DB URL secret or a migration error. |
| ALB shows targets *unhealthy* | Backend takes up to ~90 s to start (migrations). Web health check is `/login`; backend is `/api/v1/health/live`. |
| `AccessDenied` creating roles/ECS | The AWS identity lacks permissions (§3.1). |
| Image build fails on Apple Silicon | `deploy.sh` already uses `--platform linux/amd64`; make sure Docker Desktop's emulation is on. |
| Browser calls go to a strange `C:/Program Files/Git/...` URL | Git Bash path rewriting when building the web image by hand; use `deploy.sh` or set `MSYS_NO_PATHCONV=1`. |

## 10. What was actually verified (on a Windows dev machine, no Docker)

The Docker build and start-up steps were replayed natively in a clean directory against a fresh PostgreSQL 16 database:

- `npm ci` → `prisma generate` → build → `npm ci --omit=dev` (the two Docker stages) — OK.
- `entrypoint.sh`: `prisma migrate deploy` on an empty database, then API start — OK. Passing a command (the seed task) runs it instead — OK.
- Production mode: refuses to start with a missing/weak `JWT_SECRET`; seed refuses without a strong `SEED_ADMIN_PASSWORD`; `/api/v1/health/live` and `/api/v1/health` (DB check) respond; security headers present; cross-origin requests get no CORS header; the 11th wrong-password login in a minute returns 429.
- Web: `output: standalone` build with `NEXT_PUBLIC_API_URL=/api/v1`, served together with the API behind a small proxy that routes `/api/*` like the ALB — logged in through the browser and the dashboard loaded.
- `deploy.sh` passes `bash -n`.

**Not verified:** `docker build` of either image, `docker compose up`, any Terraform command, any AWS API call, HTTPS, the SSM tunnel, rollbacks.

## 11. Cheaper alternative: one EC2 server

For a pilot, `docker-compose.yml` at the project root runs everything (PostgreSQL, API, web, nginx) on a single Linux machine: `cp .env.example .env`, fill it in, `docker compose up -d --build`, then `docker compose run --rm backend node dist-tools/seed.js`. About USD 15–25/month on a `t4g.small`/`t3.small`, but **you** must look after backups, OS updates and HTTPS (e.g. Caddy or certbot). Not recommended for the final production system.
